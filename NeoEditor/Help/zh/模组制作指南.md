### 先决条件

首先，确保你阅读了这个前言。

其次，如果你不知道如何安装和使用现有的模组，你需要了解他们。因此，让我们快速回顾一下。

1. 下载 .zip 文件

2. 解压并复制内容。

3. 将所有内容粘贴到游戏的主文件夹中，即包含 NEOScavenger.exe 的文件夹。从现在起，我将其称为“根文件夹”。

4. 将模组的 `getmods.php` 文件粘贴到根文件夹中。

5. 开始游戏。

如果这不起作用，你可能需要打开 `getmods.php` 文件，确保 &strModURL 有正确的文件路径。如果没有，修正它然后继续。有关上述任何内容的更多细节，请在 Discord 上询问或查看周围。

第三，给自己补习一下 XML 文档。如果你了解节点、标签、元素和属性是什么，将会很有帮助。我个人推荐《XML 基础——初学者指南》XML Basics -- for Beginners。

一旦你学会并习惯了，这并不难。

其要点是，游戏有许多可修改的“代码块（"blocks of code"）”，这些代码块由较小的“一行命令（1-line commands）”组成，我们可以通过 .xml 文档更改这些命令的“细节（details）”。因此，能够区分哪些只是必须包含在每行中的 xml 废话，哪些是我们创建的游戏必须遵循的命令或命令的细节，这是很重要的。注意：明确一点：你不能更改诸如“strName”之类的命令名称，但你可以更改细节。

第四，你现在不需要深入研究，但当你开始深入研究 xml 时，需要了解 XSD 或 XML 架构是什么并使用它。这在接下来的介绍的概念小节中有更详细的说明。

### 介绍

#### 概念

让我们从你需要尽早考虑的事情开始。

快速失败，多次迭代。并非游戏中的一切都可以进行模组化。有些内容有其局限性，你需要测试这些局限性。这意味着要用尽可能小的样本进行测试，看看是否有效，然后再进行下一步的计划。这样可以避免你在代码中实现一个想法 2-50 次却发现它并不像你想的那样工作而浪费你大把的时间。

记录你的工作。无论出于何种原因，当你最终制作出一个有效的模组时，指的是它“不会在加载时崩溃游戏”，请牢记这一链接：Mod authors, making a better tomorrow. [示例]

模组作者的一条真实评论“重做比继续更容易”就是为什么你要认真对待这一部分。

保持备份。当你更改某些内容并确认其有效时，只需复制整个模组文件夹并放在方便的位置。这样，当它不起作用时，你可以回滚到原先的工作版本，甚至可以使用它来比较两个版本，看看哪里出了问题。不要在不加载游戏的情况下连续工作一个小时；以确保你做的一切不是无用功。[示例]

使用 XML 架构（有时也称为 XSD）。这些将帮助你发现那些会破坏模组的错误。我曾经在没有它的情况下进行模组制作，现在我学会了它，这件事我再怎么强调也不为过——使用它。这个链接（Schema for NeoScavenger.）解释了为什么以及如何更详细地说明。

### 模组是什么？

getmod.php 文件和 XML 文件集是制作一个模组的关键所在。

getmod 文件告诉运行游戏的软件你的模组是什么和在哪里，而xml 文件则是那些使模组生效的代码。

#### Getmods.php

getmods.php 文件告诉运行游戏的软件那些你要使用的模组（[示例] Example2）。当游戏加载时，它会读取 php 文件以了解模组的位置、加载顺序、是否替换现有数据以及是否有内部名称。没有它，游戏甚至不知道你的模组是否存在。

#### XML 文件集

xml 文件组成了实际的模组，这是你大部分时间将花费的地方。你会看到像这样（this example）的 xml 文件名，你所看到的是不同的“表对象类型”代码被隔离到各自的文件中。每个文件有一个或数百个“代码块（"blocks of code"）”，这些代码块都以文件顶部的 TableName 开头。

每个对象类型都在执行一个任务，通过这些行你可以直接控制该任务的内容。这就是需要我们关注的点：学习每行的作用，以及如何使这些任务实现我们想要的结果。

并不是所有的模组作者都喜欢将他们的对象类型分成各自独立的文件，原因各不相同。在上述链接中你可以看到分段的 xml 文件（segmented xml files），但当我们希望每个对象类型被分到同一个文件中时，它必须被称为 neogame.xml。像这样（Like so）。我个人更喜欢采用将所有代码整合到同一个文件的方式，而分割开进行编程的方法是游戏多年后添加的功能。

注意1：当使用单个 `neogame.xml` 方法时，不要将其放在 data 文件夹中。当使用分段式文件方法时，将其放在 data 文件夹中，不要将该 data 文件夹添加到 getmod URL 路径中。

注意2：模组由包含一个或数个 XML 文件集的文件夹组成，这意味着在 NSE 模组中，NeoScavExtended 文件夹不是模组的核心（而是堆放模组子文件夹的地方）。相反，NSExtended 和 NSEoverride 是两个文件夹，每个文件夹包含一个不同的模组。尽管这两组需要彼此才能实现其目标，但游戏将其视为两个模组。

注意3：这两种（分开或者合并） xml 方法都没有优劣之分，各有利弊，但都对游戏性能没有影响。

最后关于 xml 文件。有两种类型的 XML 文件集。我不是在谈论我们刚才谈到（[示例]）的组织方法，也不是在谈论（ObjectType）对象类型。我说的是“这组 XML 文件是在游戏中创建一个新的独特事物，还是在改变游戏中已有的事物？”。其中一种将改变游戏中现有的代码块，使其工作方式发生变化。另一种将添加全新的代码块，将一个独特的物品、疾病、场景或功能添加到游戏中。为什么我要这样说？你可以从游戏的原始文件中复制一段代码，例如吊索，然后将其粘贴到你的模组中。然后你可以将其从吊索重命名为“ThotDestroyer”。然后根据你刚刚粘贴的代码是在 `VanillaOverride` xml 文件集中（更改现有数据的 xml 文件）还是在 `AddOn` xml 文件集中（仅添加新项目的 xml 文件），它会执行两种完全不同的操作：如果你将其粘贴到 `VanillaOverride` 中，安装你的模组的任何玩家的现有吊索和所有未来的吊索将被重命名为 ThotDestroyer。如果你将其粘贴到 `AddOn` xml 文件集中，他们现有的吊索将保持不变，游戏中将有两种不同的吊索，一种名为吊索，另一种名为 ThotDestroyer。AddOn 集将新项目添加到游戏中，无论它们与其他代码多么相似。你甚至可以不更改名称，而只是让游戏中有两个名为吊索的吊索。但这会很糟糕，因为你无法分辨它们的区别。一个模组可能会使吊索发射激光……但玩家不会知道他们使用的是你的吊索还是游戏的吊索，另一个模组只会对游戏的吊索起作用。

注意：除非你正确地修改了其他模组和你的模组，否则两个吊索都可以发射激光。

所以，那个 xml 部分内容很多。我觉得 AddOn和 `VanillaOverride` 需要额外帮助来理解，所以让我们再多讲一点，以防万一你会弄混。

游戏中的每一个独特的想法、功能、场景或物品都有自己的编号。这不同于名称，因为人们也可以有相同的名称。相反，这更像是出生时分配的唯一编号（类似姓名和身份证号的区别），任何人都不能拥有相同的编号。

现在让我们回到前面那个射激光的吊索那里（我也不知道为啥文章作者突然让吊索射激光）：假设你制作了一个模组，只是复制和粘贴了原始的吊索，并将其代码放在了你的模组中。不仅仅是模组的任何部分（Not just any part of your mod though），此时你将其放在 `AddOn` xml 文件集中。这个吊索是一个纯粹的克隆体，你没有更改任何东西。

然后我们会说，原始吊索的编号是 001，而你给你的吊索的编号是 305。它们都叫吊索。当玩家在游戏中将两个吊索并排放置并悬停鼠标时，他们无法区分它们——它们看起来一模一样，但游戏知道它们的本质，并不会认为它们是同一个东西。左边的吊索是 ItemType 001，而右边的吊索是 ItemType 305。它们不是同一种物品，即使底层代码看起来一模一样。

现在让我们倒带一点，不是将相同的代码粘贴到 `AddOn` XML 文件集中，而是将其粘贴到 `VanillaOverride` xml 文件集中。这种情况下你不再有两个不同的物品，左边的吊索是 ItemType 001，右边的吊索编码也是 ItemType 001，而305则不存在。然后让我们说在你的 `VanillaOverride` 中，你将吊索重命名为 ThotDestroyer，但没有更改其他任何内容……你只更改了显示在玩家工具提示上的名称。两个吊索仍然是同一种 ItemType，因为游戏删除了与该对象类型相关的原始代码，并用你的版本替换了它。因此，当玩家尝试加载原始吊索时，他们将无法被加载，因为原始吊索的代码被覆盖了。现在只能找到 ThotDestroyer，所有过去、现在和未来的吊索都将被命名为 ThotDestroyers。到处都是 ThotDestroyers。

VanillaOverrides 实际上将你的对象类型代码块粘贴到游戏的原始对象类型代码块上……就如同你没有创建任何 xml 文件，只是直接修改根数据文件夹中的 xml 文件的操作一样，你将执行与 `VanillaOverride` 相同的操作。

注意：我们不直接编辑根数据文件夹/xml 文件有很多原因。如果你不是为了实验结束后很快彻底删除那个文件并替换它的新副本，请不要这么做。

### 总结

哦耶！工作完成了，但我们需要做一个简短的回顾。

你现在应该理解的事情：

1. 节约你的时间并保持你的代码易于理解和工作本身一样重要（做注释是一个良好的习惯）。

2. 模组由两个逻辑上可分的部分组成。getmod 文件和存储在文件夹中的 XML 文件集。

3. XML 文件集由代表不同对象类型的代码块组成。每个对象类型完成许多任务，游戏将在需要时执行这些任务。你可以通过修改对象类型中的单行来更改任务的执行方式。

4. XML 文件集可以存储/组织成两种方式：单个 `neogame.xml` 文件或几个存储在数据文件夹中的 xml 文件；文件名以它们所包含的对象类型命名。

5. XML 文件集可以是 VanillaOverrides 或 AddOns。

你不需要完全理解第一点即可完成这份指南，但完成后请认真对待第一点。

至于其余的要点，这些将在你通过本指南和你作为模组作者/创建者的日常生活中对你大有帮助。

### 详细内容

从现在开始，我们将加快步伐，使用介绍中定义的一些词汇。深入挖掘模组制作的核心。可能会变得比较难以理解。

#### Getmods.php

它回来了，它是黑色的（It's back, it's black可能是俚语吧，看不懂喵），我们在这里要征服这个野兽。我们实际上没有在介绍中多谈这个，只是提到了它是一个模组管理器。

现在是时候打开它并解释这个文件的一切。让我们从原始的 `getmod` 文件开始看看。

在上图的最顶端，我们看到文件路径，这是游戏的根文件夹，不是游戏的子文件夹。模组可以将 `getmod` 文件藏在自己的文件夹中以便重复使用和保存，但游戏从不查看这些文件夹。它只会查看根文件夹中的 `getmod` 文件以获取模组信息。哦，文件名必须是 getmods.php（区分大小写），否则无法工作。

在文件路径下面的标签中，你可以看到这确实是 `getmods.php` 文件。下面是一段看起来陌生和随意的内容。

让我们把它从图像中提取出来并专注于它。

```

`nRows`=0

```

等号左边是游戏应该加载并查找的模组数量。等号右边是这个问题的答案，此例中为零。我们告诉游戏没有模组应该加载。所以如果我可以重命名它，它会看起来像这样：

TotalNumberOfMods=NumberProvidedByTheModAuthor

TotalNumberOfMods=none

这意味着游戏运行软件读完了这个文件，并继续工作。与任何模组相关的事务（加载）都不再进行。（This means the game is done with this file, and moves on with life. Doing nothing with any mod related business.）

现在让我们选择一个实际模组的 `getmod` 文件。哪个模组？我们从流行的 NeoScavenger Extended 开始。

```

`nRows`=2

&strModName0=NSE&strModURL0=Mods/NeoScavExtended/NSExtended

&strModName1=0&strModURL1=Mods/NeoScavExtended/NSEoverride

```

我们现在有一些新的内容需要解密，但你可以将 `nRows` 视为一个“填空题和答案”。你可以认为上面的所有内容都是问题或答案。为了便于阅读，答案部分用橙色高亮显示。

因此 nRows、strModName 和 `strModURL` 是需要回答的问题。你这个模组作者手动输入这些问题的答案。游戏不会猜测或试图填写这些答案，getmod 文件也不会。

红色的数字是特别的，它既是问题也是答案，但稍后会详细说明。先认为它是对那些没有明确提出的问题的答案。

getmod 文件在提问，奇科（NSE 的模组作者）手动输入了这些答案。

所以这些内容实际上就是四个问题：

1. 这是一个 `VanillaOverride` 集还是一个 `AddOn` 集？

2. 如果是 AddOn，它的内部名称是什么？

注意：VanillaOverrides 不需要名称，所以它们没有名称。在计算机中，零（zero）表示“关闭（off）”或在这种情况下表示该 xml 文件集没有名称。它们不需要名称，因为游戏可以从缺少名称中推断出它不是 AddOn。所以你可以通过故意缺少名称来识别 Override。虽然如果你决定将其命名为“zero”而不是没有名称，也不会有任何害处，有些模组作者出于这个原因称它们为零文件。但我认为 `VanillaOverride` 更直观。

注意：内部名称不是玩家关心的东西，它们是模组作者和游戏用来与不同的 xml 文件集进行交互的。

3. 哪个 xml 文件集应该首先加载到内存中？

4. 这个 xml 文件集位于哪个文件夹中？

有很多内容需要理解，就像之前一样，让我们通过重命名这些内容来分解它们。

```
`nRows`=2

&strModName0=NSE&strModURL0=Mods/NeoScavExtended/NSExtended

&strModName1=0&strModURL1=Mods/NeoScavExtended/NSEoverride
```

```
`nRows`=2

&strModName0=NSE&strModURL0=Mods/NeoScavExtended/NSExtended

&strModName1=0&strModURL1=Mods/NeoScavExtended/NSEoverride
```

```
TotalNumberOfMods=NumberProvidedByTheModAuthor

&WhatIsXMLSetsNameRAMLoadOrder=Name&WhatFolderIsSetInRAMLoadOrder=XmlSetsFolderLocation

&WhatIsXMLSetsNameRAMLoadOrder=Name&WhatFolderIsSetInRAMLoadOrder=XmlSetsFolderLocation
```

```
TotalNumberOfMods=TwoSets

&WhatIsXMLSetsNameFirst=NSE, `AddOn` set. &WhatFolderIsSetInFirst=Mods/NeoScavExtended/NSExtended

&WhatIsXMLSetsNameSecond=Doesn't have one, Zero. `VanillaOverride` set. &WhatFolderIsSetInSecond=Mods/NeoScavExtended/NSEoverride
```

希望这能讲的足够清楚，但再说一遍。

·strModName 是在询问这个集合是否添加了新内容（如果是 `AddOn` 集），如果是，需要一个名称是什么？

·strModURL 是在询问这个集合所在的文件夹。

注意：最终包含 xml 集的文件夹可以直接放在根目录文件夹中而无需在主文件夹（即专属于你自己的mod的文件夹）中（[示例]）。虽然你也可以将这两个文件夹放在这里（here）而不放在主文件夹中。但是，请不要这样做。第一个例子会使根目录文件夹和模组文件夹混乱，第二个例子则在你制作“模组整合包”时因为使用了其他模组而导致没有主文件夹来容纳所有你使用的模组，你可能会覆盖你使用的独立模组并给很多人带来麻烦。所以请使用主文件夹并将该主文件夹放在 Mods 文件夹中。

·数字在“ModURL”或“ModName”之后立即出现，他们是加载顺序。它从 0 开始，因此 NSE `AddOn` 集将是第一个加载到内存中的集合。

注意：这很重要，如果另一个 xml 集调用了 NSE `AddOn` 集中的某些内容。如果 NSE `AddOn` 集没有在需要它的其他集合之前加载，游戏将无法加载。

·nRows 只是询问“我正在加载的 xml 集总数是多少？”

差不多就这些。如果你想知道“str”在“strModName”和“strModURL”中是什么意思：它是程序员用语，表示“字符串”。如果这让你感到困惑，不用担心，因为对我们来说意义不大。“&”符号将告诉游戏这是一个新问题的开始。

还有一些其他的事情。在 `getmod` 文件中可以有多个 `AddOn` 或 VanillaOverride，不过你不必有相等数量的两者，例如 DevKit 模组就有两个 `AddOn` 集而没有 VanillaOverrides。

好了，让我们举一个更大一点的例子来真正理解这一点。

这个例子来自另一个流行的模组 Mighty(mini) Mod of Doom（应该是MMoD？）。

```

`nRows`=5

&strModName0=FoD&strModURL0=FieldsofDead

&strModName1=0&strModURL1=FieldsZero

&strModName2=SP&strModURL2=SagesPages

&strModName3=MoD&strModURL3=M(m)MoD

&strModName4=0&strModURL4=MoDZero

```

这次我不会重命名和分解内容，我认为这已经被彻底覆盖了。然而，我要指出的是：

·是的，包含 xml 文件集的文件夹直接位于根文件夹，xml 文件集甚至没有打包到主文件夹中，但我们可以很容易地自己修复。

只需创建主文件夹，将它们移到其中，然后将主文件夹移到 mods 文件夹中。最后在 getmod URL 部分中输入完整的新文件路径。

·正如提到的，你不需要有任何匹配的 `AddOn` 和 Overrides。只需数一数“zero”名称，我就能看到这个模组有两个 `VanillaOverride` 文件集，还有三个命名的 `AddOn` 文件集。

·还有一些我们还没有提到的事情，这虽然只是约定俗成的，但很有用……他在包含 `VanillaOverride` 文件集的文件夹名称末尾加了“Zero”。这不是偶然的，他这样做是为了提醒自己该文件夹的文件集类型是什么。

最后一个名字比较长，但我有我的理由，这不是为了美观。当你离开一段时间，“zero”和“over”可能会让你更加困惑。所以在这种情况下，我更喜欢明确一点。这有助于我在不查阅资料的情况下记住。

### 表类型（对象类型）

有 24 种表类型：

- attackmodes - 处理武器可能使用的弹药/充能和战斗动作。

- barterhexes - 玩家可以在地面上买卖物品的位置。

- battlemoves - 如果它发生在战斗中，并且在屏幕左下角有一个图形，它需要/是一个战斗动作。

- camptypes - 当你在游戏中按 R 时，你会看到这些在右侧。

- chargeprofiles - 这是你定义什么 ItemType 消耗什么 ItemType 的地方。ItemType 手电筒消耗电力 ItemType 枪支消耗子弹物品。

- conditions - 这些基本上可以增加/减少游戏中的几乎任何统计数据。Philips 健康、物品的工作方式……基本上这些东西对其他东西做事情。这里有很多东西需要研究，你必须在 xml 中查看。

- containertypes - 定义物体可以适应的容器类型，并定义容器可以容纳的物体类型。

- creatures - 决定任何实体的统计数据、装备 ID 和派系。

- creaturesources - 将地图上的一个坐标点变成你设置的生物的出生点。更多信息在这里。

- datafiles - 可以通过黑客攻击和解锁软件获得的东西。

- dmcplaces - 玩家可以互动的城墙外的地方。

- encounters - 可以做很多事情的事件，包括给予或取走物品。

- encountertriggers - 事件何时以及如何触发。

- factions - 控制 AI 行为或 AI 对待你的方式。

- gamevars - 控制一些全局变量，如天气、开始日期等。

- headlines - 控制你在报纸上看到的内容。

- hextypes - 在一个六边形上的内容，其移动成本、应用的条件、光照水平、甚至一些战斗内容。

- ingredients - 用于配方中。

- itemprops - 用于将一个 ItemType 标记为一种或多种配料。

- itemtypes - 这些几乎涵盖了你在游戏中做的所有事情。

- maps - 只是猜测……1）让你决定每个坐标上的每个六边形类型。2）游戏可能在预定义的集合之间随机化……

- recipes - 如果你想在制作屏幕上制作某些东西，这就是你需要的。这不仅控制物品转化为何，还控制它们是否被使用，甚至是否应该被隐藏（如坏水）。

- treasuretables - 这是模组作者在游戏中需要生成、创建、装备的另一大支柱，这个东西基本上处理任何可能的战利品表/奖励/搜索选择。

我说模组由 PHP 文件和 XML 文件集组成。单个 PHP 文件可以将多个 XML 文件集组合成一个无缝安装。每个 XML 文件集都有一个目的，有两种类型的 XML 文件集。你可以在这里看到，有 `AddOn` XML 和 Override XML。有什么区别？总结一下，一个集改变或替换默认游戏中的现有代码，另一个集创建不会干扰默认代码的新代码。我将默认代码称为 Vanilla，因为对我来说更容易说。
